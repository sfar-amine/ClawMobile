# Q13 — staging privé des documents QA dans le SDK existant

Le propriétaire `officialGatewayOwner` partage sa découverte du package OpenClaw 2026.9.6 entre Gateway et média. Le mode privé `node dist/companion/officialGatewayOwner.js --qa-stage-document-stdin` ne charge que `plugin-sdk/media-store` : aucune lecture de configuration/authentification, aucun RPC, CLI OpenClaw ou fallback.

Contrat : une ligne JSON UTF-8 de 2 048 octets maximum contenant exactement `filename`, `contentType`, `size`, `sha256`, suivie des octets bruts exacts (1 à 20 Mio). Les noms publics sont fixes : `Claw_QA_Rapport.xlsx` et `Claw_QA_Livrables.zip`, avec leur MIME correspondant. Dix secondes maximum pour recevoir le flux. Taille et SHA-256 sont contrôlés avant toute écriture SDK. L'appel est exactement `saveMediaBuffer(bytes, contentType, "outbound", 20971520, filename)` ; le chemin retourné doit correspondre à `resolveMediaBufferPath(id, "outbound")`. Le reçu privé fermé porte `state`, `id`, `path`, `size`, `sha256`, `contentType`. Un refus ne contient qu'un code fermé, jamais les octets, une erreur brute ou des credentials. Un échec après écriture SDK est non vérifié, sans retry automatique.

Les captures nettoyées du SDK installé sur le S24 proviennent de la qualification Q13 et du commentaire Claude [196/6250854589](https://github.com/sfar-amine/samantha-ui-playbooks/pull/196#issuecomment-6250854589). Les tests consomment les déclarations, exports et corps qualifiés de `saveMediaBuffer`, avec les SHA source capturés. Un faux package installé teste la découverte et interdit même l'import Gateway ; un vrai processus CLI reçoit le protocole. Les tests couvrent fragmentation, taille/hash, champs/noms/MIME refusés et limite exacte 20 Mio. Ils sont inscrits dans le job CI existant. Aucun envoi WhatsApp ni recette physique n'est revendiqué.

Le flux reste privé, non activé : People doit vérifier son fichier/manifeste et SHA, admission/grants, replay et réservation sous son verrou SQLite existant avant staging/envoi. Pendant la matérialisation et le cleanup ponctuel, il sérialise les appels avec sa transaction `BEGIN IMMEDIATE` existante ; aucun Gateway ne s'exécute dans cette transaction.

Après sauvegarde et résolution SDK, le helper lit uniquement les métadonnées du répertoire parent fourni par le SDK, avec arrêt au 501e fichier ou au-delà de 200 Mio. Si cette borne est dépassée, il retire uniquement le nouvel ID courant vérifié avant de refuser tout envoi. Le transitoire QA est au maximum un nouveau fichier de 20 Mio ; cette admission n'est pas un quota disque global pour les autres producteurs SDK qui ne partagent pas le verrou People. Les fichiers UNKNOWN et orphelins existants comptent dans la borne, sans retry ni balayage destructif.

Après un reçu Gateway ACCEPTED seulement, People peut appeler `--qa-cleanup-document-stdin` avec JSON fermé `{filename,contentType,size,sha256,id}` (2 048 octets maximum hors LF). Le fichier est résolu de nouveau via le SDK, ouvert `O_NOFOLLOW`, vérifié régulier/taille/SHA puis dev/inode/horodatages revalidés avant unlink ; seul cet ID est retiré. Le reçu fermé est `{state:"REMOVED",id,sha256}`. Le propriétaire fournit exclusivement son reçu SDK courant, jamais un ID donné par un contact ; UNKNOWN conserve le fichier. Aucun cleanup en échec n'est présenté comme vérifié. Le SDK possède les racines et fichiers UUID. Cette fonction ne garantit pas leur rétention : la constante outbound 24 h ne prouve pas l'exécution d'un cleanup. Le propriétaire d'intégration doit qualifier la borne cumulative/rétention et le replay avant activation ; aucun nouveau GC/store n'est ajouté ici. Une écriture SDK déjà réussie peut laisser son fichier en cas de reçu non vérifié.

La limite d’admission de 20 Mio n’atteste pas encore une écriture physique de cette taille : le corps interne `writeSavedMediaBuffer` reste à qualifier pour éviter un éventuel plafond SDK inférieur. Les fixtures de limite exécutées ici sont explicitement synthétiques.
