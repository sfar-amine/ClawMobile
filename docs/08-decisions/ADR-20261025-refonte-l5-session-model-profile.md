# L5 — réglages complets, attachés à la conversation native

Statut : proposé, source seulement ; CI canonique et recette S24 requises avant activation.

R6 possède déjà les réglages des flux, leur CAS config, les confirmations, les reçus et leur retour arrière. Les valeurs précédentes doivent rester attachées aux conversations existantes, y compris compte, liste ordonnée de secours, effort, vitesse et modèle du résumé. Modifier un modèle global sans conserver ces valeurs ne satisfait pas cette règle.

La conservation utilise `SessionEntry.pluginExtensions` du SDK OpenClaw2026.9.6, sous l’extension du plugin mobile existant. Elle passe par `session-store-runtime.patchSessionEntry`, propriétaire natif SQLite partagé par Gateway et Companion. Les sources publiques capturées prouvent que cette API prépare la mutation puis relit et compare l’identité/lifecycle dans `runOpenClawAgentWriteTransaction` avant d’écrire. Aucun fichier JSON parallèle, verrou local prétendant protéger Gateway, namespace de keyed-store ou ordonnanceur n’est créé. Les réglages n’accordent aucune autorité d’exécution et ne changent aucune isolation des contacts.

Avant son `config.patch`, R6 réserve son opération dans le ledger existant, puis conserve les conversations concernées. La liste est lue une fois par agent, sans appel Gateway par ligne. Les lectures et écritures utilisent le même SDK natif. La migration est bornée à100agents,2000sessions,25secondes ; chaque écriture a une attente maximale de5secondes et vérifie son résultat par une lecture fraîche. Une génération changée ou une preuve absente refuse le changement global. Un timeout ne lance ni reprise automatique ni seconde mutation config. Une écriture metadata déjà admise peut terminer après le timeout ; elle reste idempotente et ne déclenche aucun modèle ni effet métier.

La provenance durable vient du même `config.patch` R6 admis, dans la configuration canonique du plugin. Les reçus archivables et les paramètres du client ne sont pas une autorité de configuration. Sans provenance applicable ni pin de session, le hook ne modifie pas l’héritage historique. Avec un profil admis, le contrat de consommation SDK version1 est obligatoire. Le premier tour fige les valeurs natives ; les tours suivants relisent ce pin. Les préférences explicites de la conversation restent prioritaires, puis le flux, puis le défaut. Le WhatsApp propriétaire hérite du cerveau en l’absence de profil WhatsApp explicite ; les quatre agents contacts gardent chacun leurs champs existants et leurs protections.

Le hook `before_model_resolve` existant est étendu et attendu avant la liste des candidats dans `run-entry`, puis ses champs sont consommés dans l’embedded avant auth, effort et vitesse. Le runner existant est appelé avec un filtre du seul plugin mobile à cette étape de réglages ; aucun prompt utilisateur artificiel n’est envoyé aux interprètes historiques. Le contexte par run déjà fourni par le SDK atteste la préparation du même run/session, sans nouvelle Map ni store. Il ne constitue pas un droit d’exécution. Les échecs de préparation restent fermés avant l’appel modèle ; une tentative de secours ne revient pas au modèle primaire.

La compaction applique le modèle de résumé figé aux copies de config initiale, admise et préparée. Un pin nul retire uniquement `compaction.model` et conserve le modèle courant de chaque conversation, jamais un modèle global supposé. Aucun effort ni vitesse de résumé n’est inventé. Les protections natives `modelSelectionLocked` et transcript-byte preflight restent prioritaires. Un compte explicitement suffixé est séparé du modelId puis transmis au consommateur auth natif.

Le propriétaire de compatibilité existant applique le patchset entier seulement sur la version et les empreintes de modules connues, valide tous les fichiers avant la première écriture et restaure ceux déjà écrits si une écriture échoue. Il couvre runtime et déclarations de types. `runtime-sync` contrôle/applique ce contrat et redémarre par le propriétaire existant quand il change. Les fixtures sont les sources publiques du SDK installé, avec empreintes ; les grosses déclarations sont compressées sans perte. Les scénarios I/O de tests sont explicitement rédigés, jamais présentés comme une recette S24.

Le retour arrière source ne suffit pas après un changement R6 réel : un ancien SDK ignore les pins. Il faut d’abord restaurer et vérifier les valeurs et leur provenance par le propriétaire R6, arrêter les nouvelles admissions avec les mécanismes opérationnels existants, puis utiliser le déploiement canonique et le rollback exact du patchset. Les pins/reçus ne sont pas effacés. Une perte de preuve interdit de déclarer le retour arrière ou la clôture vérifiés.


Précisions issues de la reprise du26/10 : le hook vérifie la provenance applicable à chaque flux avec le même `fieldsHash` que R6 ; une simple version de conteneur, un profil WhatsApp non applicable au cerveau ou un champ modifié hors preuve n’activent pas une sélection. Le journal R6 est consulté avant le retour neutre d’une session encore sans pin, de sorte que le tout premier changement protège aussi les sessions créées après sa liste initiale. Les conversations déjà figées continuent avec leurs propres réglages.

Une modification n’est admise que si sa version précédente peut être restaurée avec les preuves de compte et de coût actuelles. Un ancien secours Copilot non qualifié est un témoin de refus avant effet, jamais une gratuité déduite de son authentification. L’héritage conserve les champs réellement absents et le retour précédent restitue le mode automatique natif sans le convertir en booléen ; la projection utilisateur distingue automatique, hérité et non communiqué.

La vérification documentaire du 26/10 ne qualifie pas à elle seule `github-copilot/gpt-4.1`. La [documentation GitHub courante](https://docs.github.com/en/copilot/reference/copilot-billing/request-based-billing-legacy/model-multipliers-for-annual-plans) réserve les multiplicateurs aux anciens abonnements annuels conservant la facturation par requête, et sa table actuelle ne répertorie plus ce modèle. GitHub [distingue cette formule de la facturation à l’usage introduite le 01/06/2026](https://docs.github.com/en/copilot/reference/copilot-billing/request-based-billing-legacy/what-changed-with-billing). Une ancienne table indexée, un prix catalogue nul ou une authentification réussie ne remplacent donc pas une preuve de coût applicable au compte actuel, portée par le propriétaire de qualification existant. La lecture `usage.status` existante peut compléter le constat de plan ; elle n’accorde pas automatiquement cette qualification.
