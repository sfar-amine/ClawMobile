# R20 — Préparation des bornes de lecture, lot 1 non activable

Référence : fichier utilisateur 27. Base runtime `0bf30ab`. Cette PR draft prépare uniquement les primitives de sécurité et leurs tests ; elle ne livre pas encore `/v1/files` ni `/v1/files/content` et ne qualifie aucun propriétaire Gateway.

Les formes installées de `agents.files.list/get` et `sessions.files.list/get` ne sont pas disponibles dans les fixtures reçues. Les paramètres, réponses fermées, pagination, encodage de contenu, métadonnées et liens de session doivent être fournis par Claude. Aucun adaptateur ne les suppose. Aucun appel `set` ou `reveal`, accès fichier de workspace, inventaire récursif, fallback, modification, purge ni store n'est introduit.

## Primitives testées

`fileReadBoundary.ts` valide des noms relatifs normalisés NFC, refuse chemin absolu, segments vides/dot/dot-dot, caractères de contrôle, antislash, pourcentage et noms cachés. Les noms associés à context/context-backup, secrets, credentials, tokens, clés, env et auth*.json sont refusés avec un code fixe `file_not_available` (404), sans contenu. La garde paiement existante `protectedJob` est réutilisée ; son enrichissement P2-b PR #24 est une dépendance obligatoire avant toute activation du futur R20. Aucun second dictionnaire de risque financier n'est créé.

Les dossiers screenshots et ui-dumps restent en liste seule : aucun aperçu, faute de preuve canonique run/reçu non financier et non confirmation. Les primitives ne lisent jamais leurs fichiers pour ensuite essayer de les filtrer.

Le texte UTF-8 est borné à 256 Kio, avec troncature à une frontière UTF-8. Une ligne financière ou sensible est entièrement masquée : filtre P2-d, code à six chiffres, clé AWS, JWT, clés sk-/ghp_/github_pat_, adresse contenant @ et clé privée. `redacted:true` indique ce masquage ; le rendu est à son tour borné, même si les marqueurs l'agrandissent. La réponse brute, son nom et son contenu ne sont jamais journalisés par ces primitives.

PNG et JPEG sont distingués par signatures binaires, avec borne 5 Mio ; un buffer binaire inconnu est refusé. Ces tests de signatures ne qualifient pas le contenu réel d'une image comme non financier. Le futur transport devra servir les aperçus avec `X-Content-Type-Options: nosniff` et refuser les formats non pris en charge.

## Travail obligatoire avant route et activation

- Capturer et valider les quatre méthodes Gateway installées, sans accès à un secret ; distinguer ce qui est réellement couvert.
- Définir les dossiers fallback strictement autorisés uniquement pour la partie non couverte. Ancrage au workspace, `O_NOFOLLOW`, aucun symlink et aucun parcours récursif ; le volume de 790 Mio ne constitue pas une invitation à le scanner.
- Implémenter `/v1/files` avec maximum 200 entrées/page et curseur, budget 1,5 s, champs `{name,kind,size,modifiedAt,previewable}` ; conserver les inconnues sans métadonnée inventée.
- Implémenter `/v1/files/content` avec budget 2 s, garde avant lecture, limites texte/images et en-tête nosniff ; conserver 404 pour exclusions, screenshots et ui-dumps.
- Ajouter les lignes d'acceptance liste/contenu avec fixture dédiée dont l'identité est réelle, puis vérifier les budgets sur le S24 avec Claude.
- Couvrir pagination/cache/schema fermé, liens/symlinks et volume via tests du propriétaire/adaptateur réel. Les fixtures locales de cette PR ne remplacent pas ces preuves.

La CI ajoute uniquement le test des primitives, en conservant toutes les étapes. Il n'existe pas de ligne d'acceptance `/files` tant que la route n'existe pas : en inventer une donnerait une preuve trompeuse. Aucune qualification physique, P0, performance S24 ou clôture R20 n'est revendiquée. Le lot 2 d'écriture/biométrie/CAS/backups est hors autorisation actuelle.
