# R6 — configuration de l’agent main

GET `/v1/agent/config` expose la configuration main, les fallbacks exacts (suffixes `@profile` inclus), le hash CAS, l’usage agrégé limité à 100 sessions et les politiques d’outils configurées. Aucun config brut, secret ou diagnostic Gateway. Les outils effectifs restent indisponibles sans catalogue canonique.

Les modèles proposés sont l’intersection de `models.list` (`available:true`), `agents.entries.main.modelPolicy.allow` et `models.authStatus` pour main (état `ok`, `static` ou `expiring`). Un plugin explicitement désactivé est exclu. `available` vient de la résolution runtime/catalogue du Gateway ; aucun plugin inconnu n’est déclaré actif par le Companion. Le GET conserve les fallbacks configurés même lorsqu’ils ne sont plus proposés : un enregistrement ne les supprime pas silencieusement. Les niveaux de réflexion proposés proviennent de `models.list.thinkingLevels[].id`, par modèle, avec uniquement `off` si absents. Les modèles sans preuve d’authentification sont exclus ; faute de catalogue utilisable, `writeAvailable:false` et `model_authentication_proof_unavailable`.

POST `{operationId,provider,model,thinking,revision,fallbacks?,confirmationId?}` exige le flux propriétaire local sans contexte navigateur. Écriture uniquement dans `agents.entries.main.model.primary`, `thinkingDefault` et les fallbacks explicitement envoyés. Aucun repli d’écriture dans `agents.defaults` ni conversion d’`agents.list`. CAS `baseHash`, et `replacePaths:["agents.entries.main.model.fallbacks"]` pour un tableau envoyé. Les champs voisins et fallbacks omis sont conservés.

Ajouter un fallback d’un autre fournisseur ou d’un nouveau profil exige une confirmation biométrique `/v1/confirmations`, consommée avant l’effet. Action `agent.config.expand_fallbacks`, référence `main`, payloadHash SHA256 du JSON ordonné `{provider,model,thinking,revision,fallbacks}`. La présentation et l’origine sont celles de l’intention confirmée ; le core contrôle la liaison complète, l’expiration 120 s et l’usage unique. Un nouveau profil doit également être valide dans `models.authStatus.providers[].profiles`. Une baisse ou un changement principal/réflexion dans le catalogue autorisé ne demande pas de biométrie. Aucune modification de permissions d’outils n’est proposée.

Garde canonique paiement et confirmation avant réservation et juste avant dispatch, sans aucune modification bancaire. Registre des reçus existant, operationId lié au payload complet. Validation avant réservation. `ECONNREFUSED` ou échec de lancement `ENOENT` attestent l’absence d’effet : `failed`, code fixe, même opération rejouable ; les appels concurrents sont sérialisés en mémoire dans le processus existant. CAS refusé : `refused`. Une erreur après dispatch possible déclenche uniquement des relectures (trois au maximum, chacune bornée à 2 s, intervalle 200 ms), jamais un deuxième patch. Configuration observée conforme : `completed`, sinon `indeterminate` durable et non rejoué. Aucun raw stderr dans le reçu.
