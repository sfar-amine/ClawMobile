# I1 — ETag des projections de lecture existantes

Les GET `/v1/control/automations`, `/v1/providers`, `/v1/usage`,
`/v1/runs?contract=2&view=conversations`, `/v1/files` (liste uniquement) et
`/v1/agent/config` reçoivent un ETag fort `"sha256"` de leur corps JSON exact,
après projection propriétaire et nettoyage de la réponse. Un `If-None-Match`
correspondant renvoie `304`, sans corps et sans Content-Length. Un changement de
la projection donne `200` et un nouvel ETag. Le cas legacy `/runs?view=conversations`
est également couvert si le handler existant l'accepte ; le test utilise le
contrat 2 réellement paginé.

Les règles propriétaire, loopback, Origin, Referer et Sec-Fetch-Site sont appliquées
avant cette décision. Les refus, erreurs, mutations, flux, aperçus de fichiers,
réponses `deferred` ou coût en calcul ne portent pas d'ETag. Aucun changement au
paiement ni aux propriétaires de configuration, conversations, usage ou providers.
Le writer Control inclut explicitement Referer dans sa garde native avant lecture.
Le mécanisme est uniquement placé dans les deux writers JSON existants, avec une
liste fermée de routes ; il ne devient pas un routeur ou un cache parallèle.

`Cache-Control: no-store` et les en-têtes de confidentialité existants sont
conservés. Les caches et single-flight propriétaires sont inchangés. L'owner est
consulté selon son comportement existant avant de décider le 304 : l'ETag évite le
transfert d'un corps identique, pas nécessairement un appel Gateway (notamment la
lecture fraîche R6). Rien n'est stocké sur disque ou dans un nouveau cache mémoire.
`If-None-Match` accepte un tag fort/faible ou une liste valide ; `*` seul correspond
à une lecture complète existante. L'en-tête est borné à 4 Kio ; invalide, il est ignoré.

Les métadonnées de fraîcheur ne sont jamais retirées du hash. Dans Control contrat
2, une baisse de `remainingFreshMs` ou un changement de `computation` exige donc un
nouveau 200 même si `dataRevision` reste égale. Le gain des 304 y sera limité ; aucune
preuve de fraîcheur app n'est perdue par une équivalence faible inventée.

Tests CI : vrai HTTP sur les six handlers, captures natives S24 et Gateway. Les
captures natives automations et registre terminal proviennent byte pour byte de
PR #70 (SHA et hashes dans `fixtures/s24-2026-10-10/i1/README.md`). Les sources
configuration/auth/modèles/listes de fichiers sont celles déjà livrées dans
`gateway/` et `ui-recette/`. Les changements sont des variations déclarées de
ces formes réelles. Aucun endpoint factice remplaçant le handler HTTP.

La latence propriétaire injectée est celle des captures : config 4 766 ms,
usage 3 200 ms, fichiers 4 333 ms, Control natif 2 290 ms. Les lectures conditionnelles
s'appuient sur les caches existants. Le test de files observe réellement sa réponse
différée sans ETag puis attend la lecture propriétaire. Control est réchauffé via
son reader existant avant vérification du budget chaud ; son âge est contrôlé pour
prouver 304 sur corps exact, puis 200 lorsque le TTL varie. Une lecture Control
froide sans source de révision lisible reste au-delà de 1 s : I1 n'invente pas une
preuve de performance physique et ne corrige pas le comportement de ce propriétaire.

Budgets repris par AST de `companion-acceptance.py`, sans recopier les constantes :
Control automations 1 s, providers/usage 6 s, conversations 300 ms, fichiers 1,5 s,
agent/config 9 s. Aucune nouvelle route ; toutes ces lignes de recette existent.
Les tests mesurent les octets évités et les temps locaux. Le gain en production
et l'adaptation du client pour envoyer If-None-Match restent à la recette Claude.

Retour arrière : revert I1 ; les propriétaires et leurs caches restent intacts.
