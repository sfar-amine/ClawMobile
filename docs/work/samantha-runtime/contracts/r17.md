# R17 — contacts WhatsApp autorisés

Propriétaires inchangés : `channels.whatsapp.allowFrom` et `direct` via le Gateway CAS, `people-trusted.py`, People Directory et SQLite des sessions, contexte privé `memory/whatsapp/contacts/wa_<chiffres>.md`, reçus dans la table `send_receipts` existante. Aucun nouveau store, registry, scheduler ou daemon. Le paiement et ses routes sont inchangés.

Les routes sont celles du fichier 23 : GET `/v1/whatsapp/allowlist`, GET `/{contactId}`, GET `/history?limit=1..50&before=<opaque>`, GET/PUT `/{contactId}/note`, POST liste, PATCH et DELETE contact. Le contact public est `wa-` suivi des 16 premiers hex SHA256 du numéro E.164 ; le propriétaire vient de la configuration canonique, jamais de la position dans la liste. Les inconnues d'activité restent null. Les lectures sont loopback et refusent les en-têtes navigateur ; les mutations exigent aussi `x-clawmobile-owner-flow: v1`. Corps et paramètres inconnus refusés.

POST : `{operationId,confirmationId?,e164,displayName?,scope,scopeText?,durationDays,notify}` ; portée standard/claw/custom, texte custom obligatoire, durée null/1/3/5 jours, notify booléen explicite. PATCH ne contient qu'une famille : portée/texte, active/suspended, ou durée. DELETE prend operationId et confirmationId. PUT note prend operationId et texte brut sans contrôles, 2000 caractères Unicode maximum. Le bloc de métadonnées privé est borné à 2 Kio ; la note est le reste du fichier hors bloc, sans sous-bloc dédié. Les anciennes notes Markdown multilignes sont lues comme telles ; PUT garde sa borne et ses contrôles stricts. Les données privées passent dans stdin du contrôleur, jamais dans les arguments, diagnostics, reçu ou historique public.

Chaque mutation répond `{success,state,receipt,reason?}`. Reçu HTTP fermé : `{version:1,operationId,action,contactId,state,at}` ; actions added/removed/scope_changed/suspended/reactivated/extended/shortened/note_updated. Les événements expired proviennent du balayage. Historique : seuls les états terminaux added/removed/updated/suspended/reactivated, avec scope et durationDays (null si inconnu/permanent). Aucun numéro, nom ni texte de note dans l'historique public, `name:null`. Le hash de requête inclut tous les champs clients, confirmationId compris, avec action et contactId ; seuls requestHash et expectedAuthority de transport sont exclus. Même operationId/corps rend le même reçu ; une identité différente est un conflit. Aucun upload ni opération R17 n'est ajouté aux runs ou conversations.

Biométrie existante, TTL 120 s, consommée avant l'effet. Référence contactId. Hash UTF-8 des champs séparés par `|`, scopeText absent vide : add=`e164|scope|scopeText|permanent ou jours`, remove=`e164`, raise=`e164|scope cible|scopeText`, reactivate=`e164|scope conservé|scopeText conservé`, extend=`e164|permanent ou jours`. Les action.type sont `whatsapp.allowlist_add/remove/raise/reactivate/extend`. Descente vers standard ou custom→claw, suspension, raccourcissement et note n'exigent pas de confirmation. Une règle custom dont le périmètre n'est pas lisible ne constitue pas une preuve de permissions : réactivation refusée avant consommation. Le propriétaire ne peut être retiré, suspendu ou rendu temporaire.

L'adaptateur lit le reçu puis l'état canonique avant consommation ; un ajout déjà présent ne consomme pas de preuve et n'applique pas de patch. L'état attendu (présence, propriétaire, portée/texte, état, échéance) est revérifié par le contrôleur, qui préserve toutes les autres entrées et règles lors du CAS. Le contrôleur relit la confirmation consommée et son action/référence/hash. Le plan, notamment la limite de 2 Kio du bloc, est validé avant consommation. Avant tout appel à confirmations.consume, prepare valide le plan, réserve une phase avant effet dans les reçus existants et lie de façon unique la confirmation à cette opération et son hash dans les métadonnées existantes du Directory. Ce claim durable est donc écrit AVANT la consommation ; la consommation générique reste inchangée. Une panne prouvée avant effet peut reprendre le même corps/opération avec la confirmation déjà consommée uniquement si ce claim exact est encore reprenable et la preuve toujours valide ; aucune deuxième consommation, aucune réutilisation par une autre opération. Une phase pending ou un effet incertain est conservé et jamais redispatché. Le repli config set est limité aux erreurs avant l'effet. Une erreur de transport après dispatch entraîne une seule relecture de reçu, jamais une seconde mutation.

HTTP : 200 succès/idempotence ou indeterminate sans effet rejoué ; 400 invalide ; 403 propriétaire ou confirmation absente/invalide/expirée ; 404 contact inconnu ; 409 conflit/propriétaire protégé ; 503 échec avant effet, `error:allowlist_unavailable`, sans prétendre que le contact est inconnu. Lectures bornées à 10 s, mutations à 20 s, sorties à 128 Kio. Corps HTTP R17 limité à 32 Kio, y compris les échappements JSON Unicode ; après décodage/re-sérialisation, le contrôleur borne stdin à 16 Kio. Dépassement HTTP physique : 400 sans fermeture avant réponse, limites globales et paiement inchangés. Les requêtes concurrentes d'une même mutation partagent le travail en mémoire ; la vérité du rejeu reste SQLite. Aucune nouvelle source de notifications.

L'expiration reste dans le cycle existant `samantha-health-manager.sh` (environ 15 s plus contrôles), au plus une fois par minute via son état existant (whatsapp_allowlist.last_sweep, écrit uniquement après traitement d’au moins une échéance ; les passages sans effet restent bornés en mémoire). GET montre expired_pending dès dépassement. Le balayage lit uniquement les blocs R17 de 200 fichiers maximum, avec 2 Kio par bloc, puis retire les contacts échus en CAS et produit expired. Budget de 20 s par passage ; un passage incomplet reprend lors du cycle suivant. L'objectif de retrait sous deux minutes reste à qualifier sur le S24 ; aucun SLA sous panne du Gateway n'est revendiqué.
