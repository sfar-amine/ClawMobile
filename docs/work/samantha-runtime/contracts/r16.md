## Lecture et liaison

`GET /v1/runs/{runId}/approval` retourne `{success,state,receipt:null,approval,issues,observedAt}`. `approval`, si unique, a `{id,runId,summary,tool,risk,expiresAt,decidable,reason}`. États : `refreshing`, `unavailable`, `pending`, `ambiguous`, `none`.

Le GET ne lance aucune attente CLI : cache mémoire de 15 s et rafraîchissement single-flight déclenché en arrière-plan. Données froides ou périmées : explicitement non décidables. Budget global de rafraîchissement 20 s, chaque CLI bornée à 12 s ou au budget restant ; histoires dédupliquées par session et limitées à 10. Aucun refresh terminé après le budget n'est publié. Pas de timer périodique.

Les listes acceptent un tableau ou une enveloppe fermée `{approvals:[]}` / `{requests:[]}` ; les demandes acceptent `request.*` ou les champs à plat. Schéma fermé, id ASCII `[A-Za-z0-9_.:-]{1,100}`, échéance entière en ms, listes bornées à 100. Champ inconnu, type inconnu, décision inconnue ou doublon : indisponible et aucune décision. `allowedDecisions` est obligatoire pour un plugin.

Une demande exec appartient au run Gateway actif unique avec la même clé canonique de session que R2-v2. La preuve exige `sessions.list.activeRunIds` contenant **exactement ce run** ; état local `running` seul ne suffit pas. Les runs vocaux, opérations natives, résultats terminaux, expirations, suppressions et sessions archivées sont exclus. Plusieurs runs actifs, champ absent, clé différente ou runId explicite différent : aucune liaison.

Un plugin est lié au `toolCallId` exact présent une seule fois dans la transcription du dernier tour utilisateur de la session active, sans résultat de ce tool call. Aucune correspondance de texte ou de date. Sans preuve unique, le pool interne conserve `runId:null` et la route de conversation n'invente pas d'approbation.

## Périmètre décidable conservateur

Commandes, arguments, environnement, cwd, description et texte de demande ne sortent jamais bruts. Le résumé est fixe, inférieur à 160 caractères ; `tool` est seulement `exec` ou `plugin`, risque `high`. Journaux et reçus n'incluent aucun texte de commande.

Paiement, banque/carte/OTP/3-D Secure/virement, transaction/achat/checkout/facture/wallet, Topnet/Maxit/Flouci/D17/ClicToPay/termux-notification, montant suivi de devise : `approval_payment_excluded`. Les paiements et confirmations paiement canoniques actifs ou inconnus protègent également le pool ; pour un run local déjà protégé, POST refuse avant tout appel Gateway. Les détails sensibles sont non décidables.

Une commande shell opaque ne prouve pas l'absence de paiement. Seules des sondes inertes lisibles sont actuellement décidables : `date`, `uname` avec une option simple, `id` avec une option simple, `whoami`, `pwd`, `echo`/`printf` avec argument littéral borné. Cette validation locale n'ajoute aucun propriétaire ni registre. Interpréteur/script, URL via outil réseau, substitution, chaînes shell, redirection et argument opaque : `approval_payment_scope_unqualified`.

Les plugins restent lisibles et liés mais **non décidables** (`approval_plugin_payment_scope_unqualified`) : le schéma reçu ne prouve pas leur périmètre hors paiement. Un nom d'outil ou une sévérité n'autorise pas un effet. La qualification d'une preuve propriétaire supplémentaire est nécessaire pour élargir ce périmètre ; le contrat ne présente pas cette limite comme une fonctionnalité plugin terminée.

## Décision, biométrie et idempotence

`POST /v1/runs/{runId}/approval` reçoit exactement `{decision:"approve"|"deny",operationId,confirmationId}`. `operationId` ASCII `[A-Za-z0-9_.:-]{1,128}`, confirmation UUID. Aucun `allow-always`, reviewer client, grant ni durée de privilège n'est accepté.

Ordre : reçu existant lié → garde paiement locale → relecture serveur des listes/liaison active → vérification d'identité/échéance via exec.get → garde paiement/détails → vérification puis consommation de confirmation → réservation de l'opération dans le registre existant → marqueur durable d'incertitude → **un seul** resolve. Traduction `approve → allow-once`, `deny → deny`.

L'intention consommée est `agent.approval_decide`, référence = id complet de l'approbation, `payloadHash=sha256(UTF-8(id + "|" + decisionGateway))`, selon le fichier 23 qui remplace le hash initial du fichier 18. La relecture autoritative unique rattache le run. Action, référence ou hash différents refusent sans resolve ; les confirmations paiement restent isolées.

Retour `{success,state,receipt,reason?}` : `approved`, `denied`, `refused`, `expired`, `already_decided`, `failed`, `indeterminate`. Le reçu contient `{version:1,runId,targetRunId,operationId,action,approvalId,decision,state,at}`. **runId identifie l'opération native du registre ; targetRunId identifie le run de conversation concerné.** Aucun contenu de commande n'y figure.

Même operationId et requête identique : même reçu ; changement du run/de la décision/de la confirmation : conflit. Concurrence locale single-flight et claim atomique propriétaire. Un effet possible reste `indeterminate`, y compris après redémarrage ; aucun second resolve.

Échec de lecture avant consommation/réservation : `failed`, code fixe `approval_owner_unavailable`, rejouable. Une erreur typée `ENOENT` ou `ECONNREFUSED` prouvant l'échec avant dispatch du resolve donne `failed/approval_dispatch_not_started`. Sa seule reprise réutilise la preuve consommée exactement liée encore dans son TTL, l'id d'approbation identique et un claim atomique failed→indeterminate borné aux seules opérations R16. Aucun texte stderr n'est interprété comme preuve de non-effet.

En erreur après dispatch possible : une relecture de la liste correspondante, jamais un deuxième resolve. Une décision terminale explicite du même id peut confirmer le résultat ; disparition d'une liste pending **ne prouve ni expiration ni résultat**, donc indeterminate. Échéance explicite dépassée ou état terminal explicite : aucun resolve.
