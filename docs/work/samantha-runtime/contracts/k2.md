# K2 — message propriétaire après changement d’accès WhatsApp

Décision d’Amine : **aucun rappel**. Un changement effectif accordé, prolongé, retiré ou expiré produit un message au propriétaire. La prolongation conserve la biométrie et les choix actuels R17 ; les durées 1/3/5 n’introduisent aucune nouvelle décision dans ce lot.

L’implémentation réutilise les propriétaires explicitement autorisés par le [fichier 46](https://github.com/sfar-amine/samantha-ui-playbooks/blob/main/docs/work/samantha-convergence/46_Passation_Codex_session_12-10.md) et attestés par [capture 184](https://github.com/sfar-amine/samantha-core/pull/184), SHA `07be0bbb28a1947aacf97a8fa6222b4545bf594c` : `people-trusted.py` / `Contacts.mutate`, `directory.db` / `send_receipts`, `whatsapp-owner-send.sh` et le `sweep` du health manager existant toutes les 60 s. La fixture reprise est byte-identique ; aucune livraison K2 réelle n’est inventée.

## Intention et reçu dans le propriétaire R17

Avant tout effet, la réservation R17 conserve l’intention privée du message, liée à operationId, contactId et changement. La fin de mutation réussie écrit son résultat et `receipt.ownerMessage:{state,change}` dans **le même JSON de la même ligne send_receipts**, atomiquement. Aucune table ni file supplémentaire. Les notes, raccourcissements, no-op et changements non qualifiés ne créent pas de message K2. Un rejeu de la même opération relit le reçu et ne répète pas la mutation.

L’expiration réutilise exactement l’operationId canonique du sweep R17 et le retrait d’accès existant. Aucun rappel avant échéance ni scheduler supplémentaire. Un crash après effet mais avant finalisation laisse l’intention observable en `awaiting_change` dans la lecture d’opération existante. Elle demeure explicitement non qualifiée : ni mutation rejouée ni message envoyé sur un succès supposé. Ce lot ne prétend pas résoudre la fenêtre d’incertitude d’un effet Gateway externe par une transaction SQLite.

## Livraison et observation

Le sweep prend au plus un reçu pending par passage, priorité aux expirations, uniquement si 17 s restent dans son budget actuel de 20 s (timeout health manager 22 s conservé). Cela borne le travail d’un passage, **pas le volume historique ni le délai d’un backlog**. Les messages en attente restent dans les reçus R17 existants ; aucun drop ni purge d’une preuve de changement.

Le claim SQLite `BEGIN IMMEDIATE` écrit `indeterminate` avant de lancer la primitive existante. Deux sweeps concurrents ne peuvent envoyer ce reçu deux fois. La clé Gateway `k2:` + sha256(operationId/contactId/changement) distingue des changements qui auraient le même texte. Le message contient seulement la catégorie et une référence contactId vérifiable via la liste/contact R17 : ni numéro, nom, email, note privée, portée libre ni métadonnée fournisseur.

Les états sont :
- `pending` : changement réussi, livraison pas encore tentée ;
- `accepted` : la primitive a vérifié l’acceptation Gateway ; **aucune preuve de livraison au terminal** ;
- `failed_before_effect` : refus certain avant transport (argument invalide ou propriétaire non configuré), réévaluable au sweep existant ;
- `indeterminate` : timeout, crash ou réponse incertaine après admission possible ; **jamais de renvoi automatique** ;
- `awaiting_change` : intention conservée mais effet de mutation non finalisé, à observer chez R17.

Le helper canonique existant `people-trusted.py allowlist operation` sert le reçu durable ; aucune nouvelle route HTTP. La projection HTTP R17 existante filtre le champ ownerMessage, donc ce lot ne livre pas un état de notification dans l’app. Les horodatages/états de mutation et les confirmations restent inchangés par la livraison. stdout/stderr du transport sont jetés ; le journal canonique `whatsapp-outbound.log` reste chez son propriétaire, avec la clé d’idempotence pour observation par Claude. Aucune nouvelle route, capability, donnée secrète ni import privé.
