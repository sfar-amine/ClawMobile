# R11 — métadonnées de conversation

GET `/v1/conversations/{sessionId}/metadata` : success/state/receipt:null, sessionId, title, pinned, model, modelSource, mutationAvailable, issues. Session Companion exacte, vérifiée par sessions.list (clé canonique et identité unique). Valeurs non fournies par le Gateway : null avec issue, jamais un titre ou épinglage inventé. Aucun message, champ privé ou config brute.

POST même route : {operationId,title?,pinned?,model?}, au moins un choix. Titre non vide, sans contrôle, 120 caractères maximum ; booléen pour pinned ; modèle provider/model présent dans models.list. En-tête owner v1, loopback, aucun Origin/Referer. Réponses {success,state,receipt,artifact.sessionId}. Les champs inconnus sont refusés. Session introuvable 404, saisie 400, conflit ou activité protégée 409, propriétaire indisponible 503.

Le propriétaire demeure le Gateway : sessions.patch modifie seulement label, pinned et/ou model, avec key et expectedSessionId. Aucun nouveau store ou changement de runs.ts. Le registre de reçus existant lie operationId au hash de sessionId et des choix complets. Rejeu : même reçu, aucun second patch. Erreur après dispatch : une seule sessions.list ; completed seulement si les valeurs et l'identité sont observées, sinon indeterminate durable. Aucun réessai automatique.

La garde paiement/confirmation lit les propriétaires canoniques avant réservation et immédiatement avant dispatch ; aucune modification bancaire. Un changement de modèle exige hasActiveRun:false et permissionModePending:false observés avant réservation ; état absent ou ambigu refusé. Ce contrôle est une observation préalable, pas un verrou atomique du moteur. Réinitialiser un modèle vers null n'est pas exposé dans cette version.

Source de schéma : OpenClaw eb377ac, sessions-patch.ts (label, pinned, model, expectedSessionId).
