## Réponse lorsqu'une confirmation manque

Si la configuration validée étend un fournisseur ou ajoute un profil `@` non explicitement présent, la route répond **403**, sans réservation d'opération ni appel `config.patch` :

```json
{"success":false,"state":"refused","receipt":null,"error":"confirmation_required","scope":"agent.config.expand_fallbacks","reference":"main","payloadHash":"<sha256>"}
```

Les trois champs du challenge sont au niveau supérieur. Ils permettent à l'app de préparer une confirmation avec `action.type=scope`, `reference` et `payloadHash`. Le serveur recalcule le hash depuis l'objet `desired` canonique R6 : ordre fixe `provider,model,thinking,revision,fallbacks` (ce dernier seulement si fourni), UTF-8 exact. Le même hash est utilisé lors de `confirmations.consume`. `operationId` et `confirmationId` n'entrent pas dans ce hash, comme auparavant. Les références de compte publiques `acct-…` restent celles de la requête ; la résolution vers le profil propriétaire reste interne.

Le refus sans en-tête propriétaire ne divulgue aucun challenge. Les autres erreurs de confirmation gardent leur mapping existant. Le serveur ne publie que le scope fixe, la référence `main` et un hash de 64 caractères ; aucun contenu de configuration ou identifiant de compte.
