# 38 E3 — Préparation de la garde agent

## Sous-lot préparé, inactif
Le helper pur `prepareAgentCapabilityGuard` prépare le résultat du hook OpenClaw `before_tool_call`. Il n’est pas enregistré : les lectures légitimes existantes ne sont pas bloquées par un veto global ajouté à titre provisoire. Aucun appel Gateway, propriétaire ou exécuteur ; aucun état nouveau.
Le SDK public exact OpenClaw 2026.9.6 expose `ctx.requester.senderIsOwner`, `event.params`, et un retour `{params?, block?, blockReason?}`. Ce contexte diffère de celui de la factory P1, qui expose directement `senderIsOwner`.
Pour la capability ciblée, une identité host absente/invalide refuse. Une preuve interne canonique doit établir exactement `risk=read` et `operatorTarget=false`. Toute autre forme refuse `capability_first_required`. Si cette preuve est fournie, `caller` est remplacé par owner/other depuis le bit host. Les arguments du modèle risk/target/caller/decision/context ne fournissent jamais cette preuve.
La préparation lit uniquement les propriétés propres de données des objets ordinaires (ou sans prototype), sans appeler un accesseur. Une preuve héritée ou un objet mal formé refuse ; une erreur d’inspection refuse également. Les paramètres sont recopiés sous forme de scalaires indépendants, sans référence imbriquée mutable ; request doit respecter les bornes déjà déclarées du tool (texte non vide, 12 000 caractères au maximum). Cette copie ne constitue pas la liaison atomique à l’exécuteur manquante.
`AgentCapabilityPolicyEvidence` est une entrée de préparation locale, pas un schéma de reçu runtime ni une nouvelle autorité. Sa liaison à la décision canonique n’est pas implémentée. Aucun appelant produit ne peut donc accorder l’exécution avec ce helper aujourd’hui.

## Ce qui manque avant activation E3
- Lier atomiquement la preuve canonique à la décision réellement exécutée. Faire resolve puis laisser execute refaire une résolution ouvre une course ; le tool P1 actuel ne transporte pas de décision préparée signée. Ne pas inventer une autorité caller pour contourner cela.
- Le hook existant du providerFallback ne fait qu’enregistrer toolCalled ; conserver ce comportement lors de l’intégration future.
- Relance Companion à partir du userText/text du run canonique corrélé au runId host, jamais du request reformulé par l’agent. Le hook ne fournit pas directement ce texte original ; il fournit runId/messageId.
- inbound_claim traite seulement hit/known_error aujourd’hui. Réutiliser le registre de runs et les états pending/resolved/abandoned existants pour CLARIFY ; confirmer la correspondance des identités channel/run/session avant écriture.
- VoiceRelay concatène encore original et réponse ; remplacer par le resolve-clarification existant après preuve d’identité du tour.
- Gemini Live navigateur utilise fc.args.request, alors que inputTranscription sert à l’affichage. L’API capability permet un appel sans voiceTurn. Le protocole Android v2 vérifie déjà epoch/turnId et ASR/request ; ne pas l’effacer ni l’étendre par hypothèse au navigateur. Captures de contexte/liens et états voix attendues dans core #124.
