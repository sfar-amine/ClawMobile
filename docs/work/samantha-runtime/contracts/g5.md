# G5 — date du reçu de déploiement visible

Le commit court est déjà fourni par companionBuildVersion depuis #85 : aucune
copie de ce mécanisme. G5 prévoit `items[id=companion].deployedAt` dans `/v1/updates`,
ISO UTC ou null, en conservant la version npm et son suffixe de commit existants.

Propriétaire unique : G4 deploymentReceipts.ts,
`latestCompanionDeploymentAt(target): Promise<string|null>`. Ce même lecteur/cache
servira les deux lots. Seul un reçu companion `state=deployed` dont target correspond
au commit full prouvé apporte sa date `at`. Refused, rolled_back et app ne prouvent
pas la date courante. Préfixe ambigu, reçu absent ou owner indisponible donnent null.
Ni heure courante, mtime, date de manifest ni date Git ne sont substituées.

Préparation : withCompanionDeploymentDate compose cette sortie propriétaire avec
la projection updates réelle capturée `p0-3/updates.json`. Pas de lecteur de fichiers,
cache, store ou appel Gateway ajouté. Le binding n'est pas branché en production
avant fusion G4. Le test de normalisation de dates est explicitement synthétique,
pas une capture de déploiement ; le cas positif réel arrive via la capture G4 déjà
demandée, sans nouvelle demande inutile.

Bloquants : module/cache G4, capture `g4/deploy-receipts.json` (15 companion / 7 app)
et preuve d'appariement target/deployedCommit. Ensuite câbler generate dans
updatesControl et vérifier GET /updates avec son budget existant 4 s dans
companion-acceptance.py. Ajouter date sans nouvelle route/capability ; tests en CI,
union des étapes. Aucun paiement, app ou PR réservée modifiée.
