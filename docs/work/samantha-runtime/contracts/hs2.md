# HS2 — derived catalogue (preparation, blocked)

GET `/v1/catalog` reads HS1 `reporting.control_capability --catalog --locale fr|en` from `controlPaths().playbooks`: configured snapshot, pinned current, then existing workspace fallback. It never invokes Graph construction, execution, Gateway, supplier, payment payable loading, laptop status or network guard. The presentation is a derived view, never an executor or a parallel registry.

The route requires loopback and rejects Origin, Referer and Sec-Fetch-Site before reading or evaluating an ETag. GET only, no query parameters. Accept-Language selects English when it starts with en; French otherwise. `Vary: Accept-Language`, Content-Language, private/no-cache and a strong hash of the exact response support conditional 304 responses.

The existing ControlReadPool shares reads and caches the result for at most 15 seconds, within its existing 16-key/2 MiB bounds. This route limits native output and projection to 256 KiB, 32 themes, 128 groups total and 512 actions total. Theme/group/action identities and default pins must be unique and reference the declared hierarchy; orders are bounded integers, timestamps ISO UTC, slots unique and labels bounded. Unknown owner, gate, badge or account fields are discarded; the caller cannot turn them into runtime evidence. The owner locale must match the requested locale. The child has a 6 s hard timeout and participates in Control cancellation. HTTP target is 300 ms, including cold responses. After a 200 ms deadline, a cold generation returns an explicitly unavailable envelope (`reason:catalog_computation_pending`, `computation.deliveryMode:deferred`) without catalogue entries or ETag. The existing shared owner flight continues; the next GET observes its result. This is not catalogue data or an available state. The existing acceptance settle loop must receive a real projection within 15 s, and fails if it remains deferred or its owner errors. No warming before listen is presumed. TTL expiry or a selected snapshot path change uses this same bounded-response strategy.

HS1 currently provides presentation, but its CLI does not inject a proven Graph reachability, runtime route-health or armed owner gates. Therefore this preparation **does not enable any action**. Backed capabilities keep their identity but carry `available:false`, `request:null`, `reason:readiness_evidence_unavailable`. Unbacked entries keep `capability:null`, `available:false`, `reason:in_development`. Transaction kinds preserve confirmationRequired:true. HTTP parameters cannot arm a gate. No owner admission is inferred from an input boolean or registry status.

`inputs.voiceMemo:false` remains explicit until HS8 owner qualification (core issue126). `badges:[]` is explicit: no live data is substituted for existing receipt/cache evidence. The final HS2 owner projection needs confirmed read-only Graph/health/gate/badge sources plus a cleaned S24 catalogue capture; source qualification is tracked in paired playbooks PR69 and existing questions, without a duplicate request.

Tests use actual **Git HS1 projections** from playbooks d166778058eb7739100f2ad454fd5e066c7c3d7a. They are clearly separated from runtime fixtures and cannot prove S24 readiness. The HTTP test traverses the actual server and Control pool, injects a conservative 2.3 s source delay, verifies ten requests share one generation, cold response under300ms without invented entries, settling after owner completion, warm p95 under300ms, locales, 304, owner errors returning503, cross-origin refusals and zero live-owner calls. Neither this injection nor the local warm measurement is a S24 benchmark. The CI registers the test; acceptance registers `/catalog` with target0.3s. Draft remains blocked until real capture and complete availability/badges contract are verified.
