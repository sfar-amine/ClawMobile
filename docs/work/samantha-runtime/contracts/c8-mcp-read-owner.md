# C8 — lectures MCP sous le reçu RemoteBridge existant

Ce lot prolonge l'enveloppe facultative C5 (`148dbff8`). Les anciens clients ne changent pas. Il ne crée ni outil public, méthode de pont, exécuteur métier, store, routeur ou état de dialogue. Les écritures et références serveur sans admission propriétaire restent fermées.

Le propriétaire RemoteBridge revendique durablement la demande (`received`, puis `running`) **avant toute interprétation ou lecture**. Il conserve les mêmes `requestId`, `taskId`, `stepId`, profil admis, conflits de paramètres et reçus. Le nouveau chemin utilise la méthode existante `mcp_capability_execute_readonly`. Les paramètres ne contiennent que le protocole et l'empreinte canonique calculée par le host depuis le paquet validé ; ni transcript ni instruction cliente ne sont persistés. Cette empreinte prouve une identité de contenu, jamais l'autorisation.

La provenance en processus existante (`authenticatedMcpAccess`, WeakMap) porte une fonction de lecture privée pour la durée de cette demande. Un JSON public ne peut fournir cette fonction ou une autorisation équivalente. Le dispatch refuse une enveloppe de ce protocole sans son admission privée, sans retomber sur l'ancien résolveur. Un callback attaché à une méthode d'écriture est refusé. Une exception du callback devient un code fixe parmi `mcp_read_protocol_required`, `mcp_read_deadline_exceeded` et `mcp_read_execution_failed`. Toute autre exception est réduite au dernier code ; aucun message privé n'est recopié. La réponse MCP, `claw_status` et le rejeu conservent cette même cause bornée.

Le callback appelle une fois le port C4 `intentReadOnly`, sous les protocoles `mcp-input.v1` et `mcp-read.v1`, avec le contexte via FIFO et les identités d'événement dérivées par le host. B interprète et exécute dans **la même instance Python**, sans sérialiser `ValidatedInterpretation` ni aucun grant. L'exécution Graph doit imposer `read_only=True` ; le nom d'une méthode, le risque déclaré par un client ou une réponse JSON ne fournissent pas ce droit. Aucun DialogueStore de fil MCP n'est créé ou utilisé par ce mode. Sans port de lecture compatible, le verrou C5 demeure `INTERPRETATION_OWNER_RECEIPT_REQUIRED` ; sans port d'entrée, `INTERPRETATION_HOST_UNAVAILABLE`.

Un succès métier requiert le statut natif `hit` et un état d'exécution `completed` ou `partial`, avec les deux protocoles privés attestés. Les échecs et les résultats `running`/`indeterminate` restent visibles comme tels. Les métadonnées d'interprétation sont bornées à la projection de reçu du host, sans prompt, sortie générée complète ou transcript. Le reçu transport peut être terminé sans que la lecture ait réussi ; `claw_status` conserve cette distinction.

Un appel concurrent de même action/étape observe le reçu déjà revendiqué et n'interprète rien à nouveau. Un contexte différent sous la même identité donne un conflit 409, même si le texte courant ne change pas. Un reçu terminé ou incertain reste consultable et rejouable en lecture de statut quand le port IA est indisponible ; il ne reconstruit pas le callback après un redémarrage. Le propriétaire existant conserve sa normalisation des reçus périmés et sa réconciliation. Les lectures longues ont la même réponse bornée `running` que `exec_wait` ; la fin écrit le reçu existant, sans nouveau moteur de retry.

La preuve locale de ce lot porte sur la frontière Node, avec des callbacks synthétiques, et sur les régressions existantes. Le test apparié du complément C4/B doit encore prouver le refus d'une intention d'écriture par le vrai Graph `read_only`, la conservation en mémoire de la preuve et le protocole privé complet. Les tests de transport ne remplacent ni ce test apparié ni une qualification des profils DATA ou du MCP réel. Aucun modèle, effet métier ou téléphone n'est appelé par ces sondes. La CI canonique exacte et la recette par Claude restent distinctes.
