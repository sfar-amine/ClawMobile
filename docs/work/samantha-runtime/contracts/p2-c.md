# P2-c — demande REQ et annulation canonique

Base playbooks : main fa41d20. Base Companion : pile locale R2-v2/R5/V2/V4/P2-a après runtime da19e89. Aucun paiement, banque, biométrie ou reçu bancaire n'est modifié ; aucune nouvelle source de vérité.

GET /v1/control/requests/{REQ-n}?contract=2 conserve la projection v2 et fournit steps[] {label,at,state}, facts[] {key,label,value}, sessionId:null, currentAction (expectedAction existant filtré, null après clôture), cancellable. Les dates sont celles des événements Memory Core du même groupe ou de l'action Situation ; aucun upcoming ni sessionId deviné. La liste ne porte que les champs résumés et cancellable. Les détails sensibles sont masqués ; les détails libres de paiement et le contenu bancaire d'une action gérée par un autre propriétaire ne deviennent pas des facts. Une source illisible rend l'action non annulable.

POST /v1/control/requests/{reference}/cancel, corps strict {operationId}, natif loopback owner (x-clawmobile-owner-flow:v1), sans Origin/Referer/sec-fetch-site. Réponse {success,state,receipt}, state cancelled|already_closed|not_found|refused|indeterminate. HTTP 409 pour refused, 404 pour not_found, 400 pour requête invalide. reason est un code fermé, jamais un diagnostic brut. Aucun request_id fourni par l'app n'est accepté.

La façade appelle python3 -m reporting.control_actions cancel-request dans les playbooks épinglés. Le module résout REQ et les supersedes avec le resolver partagé. Famille T : context-event.sh écrit completed_action avec REQUEST_CANCEL_V1 et supersedes de l'événement canonique. Famille H : withdraw exige managed_by=situation et pending, passe à withdrawn dans SituationStore, puis sync_owner_requests projette la clôture Memory Core avec outcome=withdrawn. Le statut partagé ANNULÉ est projeté cancelled ; les clôtures antérieures restent TERMINÉ.

Paiement : la classification de refus utilise le même _owner_request_group et TOPIC_RULES que le reporting. Le code fa41d20 ne contenait pas les entrées paiement/banque annoncées dans la précision ; elles sont ajoutées à cette table canonique partagée, sans classificateur parallèle dans le Companion. Les actions humaines gérées par un autre propriétaire sont refusées. Le test bancaire vérifie l'absence de writer, de réservation Companion et de changement Memory Core/SituationStore.

Idempotence : intentId=sha256(operationId+reference). SituationStore utilise cette identité de mutation. Pour T, context-event.sh reste propriétaire de l'identifiant immuable effectif (hash surface/kind/supersedes/body) : cet identifiant n'est pas remplacé arbitrairement par intentId. Le payload contient operation_id/reference/intent_id, et le reçu retourne intentId et eventId distincts. Un retry retrouve le même événement, même après redémarrage. La fermeture annule aussi les anciennes mises à jour du groupe, pour qu'une ancienne demande ne réapparaisse pas.

Le Companion réserve le dispatch dans son registre de runs existant après préflight canonique. Un résultat de processus incertain autorise une lecture de confirmation seule ; il ne déclenche pas un second dispatch. Un retrait H sans projection reçue reste indeterminate ; la réconciliation existante peut projeter ultérieurement, sans refaire withdraw. Une sortie réussie du helper ne prouve pas une écriture : seul Memory Core confirme le reçu. Les refus bancaires sont évalués avant toute réservation.
