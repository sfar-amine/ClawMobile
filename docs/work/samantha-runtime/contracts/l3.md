# L3 — Description de PR conforme au modèle

Le workflow CI core exécute `tools/check_pr_template.py`. Pour un événement
`pull_request`, il lit le JSON désigné par `GITHUB_EVENT_PATH` et les titres de
niveau 2 de `.github/pull_request_template.md`. La description doit contenir
chacun de ces titres exacts (casse, accents et ponctuation). Aucune vérification
sémantique des explications ou des cases cochées n’est revendiquée.

Les titres placés dans des commentaires HTML ou des blocs de code ne comptent
pas. Le corps est traité uniquement comme du texte ; jamais exécuté ni affiché.
La sortie expose uniquement des sections du modèle manquantes et des codes fixes.

## Calendrier explicite

Semaine d’avertissement : **11 octobre 2026 00:00 UTC au 18 octobre 2026 00:00 UTC**.
Avant cette période aussi, une non-conformité reste un avertissement. À partir du
**18 octobre 2026 00:00 UTC**, elle renvoie le code 1 et bloque la CI.
Le calendrier fixe est dans le code ; aucun store ou compteur d’activation.
`--now` permet d’injecter une horloge ISO avec fuseau pour les tests.

Un push est `skipped`. Sans événement, une invocation locale est également
`skipped`, mais `GITHUB_EVENT_NAME=pull_request` sans chemin est une erreur.
Un payload PR absent, invalide ou trop gros suit le même calendrier de sanction.
Les limites sont de 2 Mio pour le JSON et 1 048 576 caractères pour le corps.
Un modèle vide est toujours une erreur de configuration.

## Portée et preuve

Dix tests utilisent des payloads GitHub **générés**, pas des captures S24 :
modèle complet, manque, bascule exacte, titres factices, injection textuelle,
absence de payload, push, limites, horloge et workflow sûr. Le workflow reste
`pull_request`, sans `pull_request_target` ni permissions supplémentaires.
Les étapes existantes sont conservées. Les événements `edited` et
`ready_for_review` relancent aussi le contrôle lorsque la description change.

Ce lot ne lit aucun runtime et n’ajoute aucune route Companion. Budget/recette
S24 et fixture S24 sans objet. `NO_CAPABILITY` : contrôle de livraison GitHub.
Le contrôle lit le modèle propriétaire core, qui exige notamment `Retour arrière`
(et non le titre d’activation propre aux playbooks). La PR jumelle playbooks
utilise son propre modèle, sans checkout ni lecture inter-dépôts en CI.
Retour arrière : revert de cette PR. Aucun déploiement ni migration S24.
