# E3 — R20 lot 2 : modifier un fichier de l'agent

Fichiers 27 (R20, lot 2), 34 (bloc D) et 35 (E3).

## Route

`PUT /v1/files/content?scope=agent&path=NOM`, garde owner (boucle locale, sans Origin, `x-clawmobile-owner-flow: v1`),
corps `{operationId, content, baseHash, confirmationId?}`, budget 20 s (CLI : `agents.files.get` 3,45 s capturés,
`agents.files.set` du même ordre, relecture éventuelle). Capability `samantha.app.agent_file.write` (planned, biométrie)
dans la PR playbooks jumelle. `POST /files/content` reste 405 ; sans en-tête owner, toute écriture reste 403.

La lecture `GET /v1/files/content?scope=agent&path=NOM` publie désormais `revision` : le sha256 du propriétaire,
vérifié égal au sha256 des octets lus. C'est le `baseHash` de l'écriture.

## Ordre

1. Validation : nom, corps fermé, contenu UTF-8 sans NUL de 256 Kio au plus (borne de l'aperçu : le propriétaire
   approuve ce qu'il a pu voir en entier), `baseHash` sha256, `operationId`.
2. Lecture owner `agents.files.get` ; sha256(contenu) doit égaler `hash` (sinon 503). Fichier absent : 404.
3. CAS préalable : `baseHash` ≠ révision courante → 409 `file_revision_changed` avec `currentRevision`.
4. **Garde des secrets et identifiants.** Les lignes protégées utilisent le propriétaire de la lecture
   (`protectedFileLine` de `fileReadBoundary.ts`). L'app édite l'aperçu masqué : chaque ligne `[masqué]` représente,
   dans l'ordre, une ligne protégée du fichier courant et est restituée telle quelle. Nombre différent → 422
   `file_protected_lines_changed` ; nouvelle ligne sensible ou marqueur ambigu → 422 `file_content_protected`.
   Contrôle final : la suite protégée du résultat est identique à celle du fichier courant.
   **Décision du 11/10, dépendance H6 (#104)** : aucun mot de paiement n'est bloqué. Le précédent motif lexical
   doit être retiré chez le propriétaire partagé avant qualification de cette PR ; les protections structurées
   (hôte, invocation, confirmation et CAS) restent obligatoires. Les comptages historiques de lignes paiement
   capturés dans #131 ne constituent pas une règle de filtrage à conserver.
5. Contenu identique après restitution : 200 `unchanged`, sans confirmation ni écriture.
6. Sans `confirmationId` : 403 `needs_confirmation` `{scope:"agent.file_write", reference:NOM, payloadHash:sha256(contenu envoyé)}`.
7. Opération native (reçu dans le registre des runs) : consommation de la confirmation ; **sauvegarde** de la version
   courante ; **un** `agents.files.set` avec `expectedHash = baseHash`. Conflit natif → `refused / file_revision_changed`.
   Réponse incertaine → **une** relecture : nouveau hash → `completed` ; ancien → `refused / file_write_not_applied` ;
   relecture impossible → `indeterminate` (503), jamais de rejeu. Même `operationId` → reçu stocké.
8. `completed` vide le cache des lectures de fichiers.

## Sauvegardes

La Gateway n'en fait pas et aucun propriétaire « 5 sauvegardes » n'existe (#131). Le Companion écrit, avant l'effet,
`<NOM>.bak-samantha-<AAAAMMJJTHHMMSSmmmZ>` dans le workspace de l'agent, à côté du fichier, selon la convention déjà
présente (`AGENTS.md.bak-ui-playbooks-*`) : création exclusive, sans suivre de lien, mode 0600, puis purge pour n'en
garder que 5 sauvegardes `<NOM>.bak-samantha-*` par fichier. Les anciennes sauvegardes `.bak-ui-playbooks-*` appartiennent à l’installateur et ne sont pas purgées par cette route. Ces noms sont masqués des lectures par `fileReadBoundary.ts` (`.bak`). Aucun nouveau store,
registre ni démon. Échec de sauvegarde : `refused / file_backup_unavailable`, sans écriture.

## Limites

- Le CAS natif ne sérialise que les écritures `agents.files.set` d'un même process Gateway ; un autre écrivain
  (`install-openclaw-instructions.sh`, outil de l'agent) n'est pas sérialisé. La relecture le détecte, sans rejeu.
- `AGENTS.md` est aussi réécrit par l'installation des playbooks : une modification depuis l'app peut être remplacée
  au prochain `install-openclaw-instructions.sh` (sauvegarde `.bak-ui-playbooks-*` de ce script).
