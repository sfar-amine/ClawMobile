# G2 — Inventaire des contrats HTTP, lecture seule

Base de référence : `af4132a038727d2a3a54e4d5353d003f08d9f174`. Cette livraison prépare le contrôle des contrats ; elle ne clôture pas la qualification G2 sur S24.

Le runner `openclaw-plugin-mobile-ui/scripts/runtime-contract-report.py` lit le manifeste versionné `runtime-contract-cases.json` (120 cas). Il effectue exclusivement des GET sur l'adresse littérale loopback du Companion, port 8765 par défaut. Il n'envoie aucun en-tête propriétaire, aucune confirmation ni mutation. Les redirections et les proxys sont désactivés. Chaque lecture reste bornée à 2 Mio et une tentative, même après erreur ou timeout. Le timeout de transport est calculé depuis READS de installer/termux-lite/companion-acceptance.py, avec une marge de 2 s : chemins normalisés sans query et maximum en cas de doublon. Les routes non encore inscrites gardent 3 s. Il n’existe aucune seconde table manuelle de budgets. --timeout impose explicitement une borne de0,01 à30s. Le rapport ne transforme pas cette marge en preuve de respect du budget de recette.

```sh
python3 openclaw-plugin-mobile-ui/scripts/runtime-contract-report.py \
  --base-url http://127.0.0.1:8765 \
  --output /tmp/runtime-contract-report.json
```

Un fichier `--bindings` peut fournir les paramètres des routes dynamiques, par exemple `{"request-detail":{"params":{"id":"REQ-123"}}}`. Seuls les paramètres exactement attendus sont acceptés ; il ne peut modifier ni route, ni méthode, ni statut du cas. Aucun identifiant fourni n'est copié dans le rapport. Utiliser les noms de paramètres du manifeste, pas cet exemple sans les vérifier.

Le manifeste distingue `active`, `pending`, `offline`, `unknown` et `excluded`. Chaque cas est obligatoire, sauf les exclusions de transport sensible et de paiement documentées. `pending` cite les PR non intégrées (#14, #24, #26, #28, #30, #34, #36, #39 et #41), `offline` exige une recette propriétaire dédiée ; `unknown` exige l'inventaire final des méthodes et formats. Ces cas, ainsi que les paramètres manquants, interdisent `complete:true`. Le GET `/v1` fournit uniquement un contrôle de dérive : son absence d'une route récente ne supprime jamais un cas du manifeste. Le manifeste complet est imposé ; aucun sous-ensemble externe ne peut remplacer l'autorité versionnée.

Les mutations P2-a/P2-c, la biométrie P2-f/R16/R17, les imports P2-d et le stockage R14 restent hors de ce runner. Leurs tests dédiés sont référencés quand connus, sans inventer de résultat. Les cas inconnus ne sont pas arbitrairement promus en GET. Un cas de lecture sans contraintes de format indique uniquement une réponse JSON objet : il ne prouve pas le contrat détaillé de l'écran. Les propriétaires doivent compléter ces contraintes à partir du code fusionné et de la recette.

Le rapport contient uniquement les références publiques du manifeste, verdicts, codes HTTP, durées et nombre de tentatives. Il ne contient ni corps de réponse, paramètres de route, URL, opération, contenu de fichier, nom, numéro, note ni texte d'erreur. Un contenu ressemblant à un secret produit `secret_detected`, sans conserver sa valeur. La détection n'est pas une preuve universelle d'absence de secret ; la protection principale est l'absence de copie des réponses.

Les champs `physicalQualification:false` et `mutationQualification:false` sont toujours présents. `complete:true`, si l'inventaire est un jour entièrement qualifié, concernera uniquement les lectures HTTP décrites, jamais le paiement, la biométrie réelle, l'audio, la route duplex, M1 ou le RDV1. Avec le manifeste présent, la sortie attendue est `incomplete` (code 2). Code 0 signifie seulement l'ensemble des lectures applicables passé ; code 2 indique une configuration rejetée ou une couverture incomplète. Le mode fixture du module Python émet toujours `complete:false`, même quand ses seuls cas passent.
