## Raccordement et propriétaire

`callOpenClawGateway` garde sa signature, ses paramètres et `expectFinal`, mais passe désormais par un unique `PersistentGatewayTransport` créé paresseusement dans le processus Companion. Tous ses callers utilisent ce chemin commun ; aucun appelant de paiement n'est modifié. `GatewayClient`, `loadConfig`, `resolveGatewayPort`, `resolveGatewayAuth` et `resolveSecretRefValues` proviennent exclusivement des exports publics du paquet OpenClaw 2026.9.6. Le SDK conserve le protocole, le handshake et la reconnexion. Aucun lecteur maison de credentials, protocole parallèle, store ou processus permanent n'est ajouté.

La résolution du SDK utilise le module installé, puis le paquet OpenClaw sélectionné par le binaire CLI existant, y compris une installation globale avec lien symbolique. Import ESM natif dans le Companion CommonJS. Aucun secret, environnement ou configuration résolue n'est affiché. Les loggers du client sont neutralisés.

Le raccordement pris en charge est volontairement fermé : Gateway local loopback, sans TLS, authentification locale token/password ou mode none. La configuration et le port sont lus par leurs propriétaires SDK. Les seules références d’authentification nécessaires au mode sélectionné sont résolues en mémoire par resolveSecretRefValues ; aucune référence d’un autre champ ou mode n’est lue, aucun credential n’est persisté ou affiché. Une configuration remote, une URL explicite, TLS, un mode d'authentification différent ou une version SDK différente sont refusés avant envoi, sans repli qui contournerait ce refus. Ces configurations nécessitent une adaptation qualifiée du bootstrap canonique, pas un second lecteur de secrets.

Identité client CLI, mode CLI, rôle operator, protocole 4. Pour le Gateway local avec authentification partagée, deviceIdentity:null réutilise la politique locale du propriétaire CLI, sans créer de nouvelle identité. Scopes persistants fermés aux besoins des callers actuels : operator.admin/read/write/approvals. Les scopes questions/pairing/talk.secrets ne sont pas demandés. Cette union réduite n'est pas une imitation des sept scopes par défaut du CLI ; sa qualification S24 est demandée à Claude.

## Admission, délais et effets

Une connexion de transport n'est jamais une preuve d'admission : les RPC attendent `onHelloOk`. Fermeture ou erreur efface cette preuve. Quatre RPC actifs maximum, 32 en queue, paramètres capturés et limités à 256 Kio. La deadline couvre initialization, attente, queue et appel ; le SDK reçoit le budget restant et un AbortSignal. Une expiration en queue est prouvée avant effet.

Le repli CLI conserve le propriétaire existant uniquement avant envoi lorsque le socket est indisponible ou le paquet SDK est absent, sans requête SDK commencée. L'absence du SDK est une indisponibilité de transport explicite ; elle ne constitue pas une preuve de socket joignable. Un timeout d'admission ou un refus d'authentification/configuration/protocole ne permet aucun repli. Le CLI reçoit uniquement le temps restant.

Après la frontière SDK.request, une coupure, une exception ou une expiration reste indeterminate ; aucun repli CLI ni redispatch de cette requête, même après reconnexion. L'appelant conserve ses vérifications d'effet et son operationId/idempotencyKey. Les seules réponses CAS sûres projetées sont les trois INVALID_REQUEST fixes du propriétaire config : base hash unavailable, base hash required, config changed since last load. Elles deviennent `gateway_config_revision_conflict`, message fixe `config baseHash conflict`, effectNotStarted:true. Aucun message/details arbitraire n'est rendu. Les autres INVALID_REQUEST structurés gardent leur code avec un message fixe sans affirmer l’absence d’effet ; CRON_JOB_NOT_FOUND et FORBIDDEN/MISSING_SCOPE capturés sont des refus avant effet, les erreurs inconnues restent incertaines.

La fermeture du Companion arrête le client partagé ; les jobs en queue sont refusés et aucun job actif n'est rejoué. Une initialisation tardive après arrêt ne démarre aucun client.
